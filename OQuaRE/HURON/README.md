# HURON use case

Evaluation of the human readability of the OQUO core with [HURON](https://github.com/tecnomod-um/huron), whose results are represented as OQUO-compliant RDF according to the [OQuaRE quality model](../README.md#the-oquare-quality-model).

HURON (HUman Readability ONtologies) measures the names, descriptions and synonyms of the classes and properties of an ontology, and the lexical regularities and systematic naming of its labels. It generates its results as OQUO-compliant RDF itself, described with its own OQUO module, [`oquo-huron`](https://purl.org/oquo-huron) (`https://purl.org/oquo-huron`), maintained in the HURON repository. The module defines:

- the metrics of HURON, associated with the characteristics of the OQuaRE quality model they measure;
- the raw scale of each metric, and its conversion to the five categories of the OQuaRE quality model;
- the issue types that HURON reports;
- the software agent of HURON (`oquo-huron:huron-software-agent`), to which the results are attributed.

## Contents

| File or folder | Content |
|---|---|
| `evaluate.sh` | Script that downloads the OQUO core, evaluates it with HURON and applies the `oquo-huron` module to the results. |
| `source_results/` | Results of HURON, as generated by its command-line tool (`huron_results.ttl`), and the versions used to obtain them (`environment.txt`). |
| `oquo_compliant_results/` | The results of HURON as OQUO-compliant RDF, with the `oquo-huron` module and the converted values (`oquo_model.ttl`). |

## Reproducing the results

The evaluated ontology is version 2.2.2 of the OQUO core (`https://purl.org/oquo-core/v2.2.2`), evaluated with HURON 0.0.15.

HURON is not part of the [services](../../services/): it is run with its command-line tool, which needs the HURON jar (`huron-0.0.15.jar`, available in the [releases of HURON](https://github.com/tecnomod-um/huron/releases)) and Java, or Docker to run it without a local Java. The `oquo-instance-creator` service is used to apply the `oquo-huron` module to the results, so start the services first (see the [main README](../../README.md#running-the-services)):

```bash
cd services
docker compose up -d --build --wait
```

The command-line tool does not accept an IRI as input, so the ontology is downloaded first:

```bash
curl -fsSL -H "Accept: application/rdf+xml, text/turtle;q=0.9, */*;q=0.5" \
     https://purl.org/oquo-core/v2.2.2 -o /tmp/oquo-core.owl
```

and then evaluated, from this folder:

```bash
java -Xmx8g -jar huron-0.0.15.jar \
     --input /tmp/oquo-core.owl \
     --output-detailed-rdf source_results/huron_results.ttl
```

HURON gives only the results of its metrics, on their raw scales. To add the `oquo-huron` module, with the ontologies it imports, and the values converted to the five categories of the OQuaRE quality model, the results are sent to the `/applyModel` method of the instance creator:

```bash
curl -X POST "http://localhost:8000/applyModel" \
     --url-query "ontologyIRI=https://purl.org/oquo-huron" \
     -H "Content-Type: text/turtle" \
     --data-binary @source_results/huron_results.ttl \
     -o oquo_compliant_results/oquo_model.ttl
```

The three steps are run by `evaluate.sh`, which downloads the ontology to a temporary file, removed at the end, and records in `source_results/environment.txt` the versions used: the ontology and the checksum of the content evaluated, the HURON jar and its checksum, the Java version and the OQUO module applied.

```bash
./evaluate.sh
```

The script expects the jar in this folder; to use another one, give its path in `HURON_JAR` (e.g. `HURON_JAR=/path/to/huron-0.0.15.jar ./evaluate.sh`). If Java is not installed, it runs HURON in a Docker container (`eclipse-temurin:17-jre` by default, which can be changed in `JAVA_IMAGE`). HURON uses up to 8 GB of memory, which can be changed in `HURON_MEMORY`.

It evaluates the OQUO core 2.2.2 by default; to evaluate another ontology, give its IRI: `./evaluate.sh https://purl.obolibrary.org/obo/go.owl`.
